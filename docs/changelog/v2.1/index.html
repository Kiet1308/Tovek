Tovek V2.1

  1. (1)Introduction
  2. (2)Performance and speed
  3. (3)Reliability

We’re introducing Tovek V2.1, the first update to the V2 generation. It decompiles a full Roblox game 1.7× to 2.1× faster than V2, reads Luau bytecode v14, and fixes every case we found where decompiled code could behave differently from the original script.

Since V2 shipped, the decompiler has been through three independent code reviews and a week of focused performance work. The reviews looked for one thing above all: places where the code Tovek writes runs differently from the code that was compiled. Everything they found is fixed in V2.1, and every case is now a permanent test that each future release has to pass.

Here are some of the improvements you can expect from V2.1:

Speed. V2.1 decompiles our 3,978-script test game in 11.5 seconds on a single thread, down from 20.1 seconds with V2. With every core busy it finishes in under a second. It’s faster at every thread count we tried, and it uses less memory while doing it: peak memory at 16 threads fell from 122 MB to 103 MB. Scripts sent through the local server come back 1.5× faster overall, and large ones up to 2.5× faster.

Correctness. V2 could occasionally write code that looked right but didn’t act right: a saved copy of a variable read after a call had already changed it, a write inside an if applied unconditionally, a replaced Vector3 global quietly bypassed. V2.1 fixes all of them. On our deep-review suite of 199 behaviour checks, V2 passes 80; V2.1 passes all 199.

Newest bytecode. Luau bytecode v14 now decompiles directly, and its new fast path for pcall and xpcall comes back as the plain call you wrote. V2 couldn’t read these files at all.

Reliability. Damaged, truncated or deliberately malformed bytecode is now checked before any analysis starts. In our tests V2 aborted on 6.9% of damaged files, often without a word; V2.1 never did. It tells you what is wrong and where, like prototype 0, pc 0: invalid jump target, and one bad script no longer takes a whole batch down with it.

A steadier local server. The HTTP server now lines requests up in a fair queue instead of reading every upload at once, starts each job as soon as a slot is free, and puts a firm deadline on slow uploads.

The next major updates to Tovek will follow in the coming weeks, with much larger improvements to readability, naming and speed.

Performance and efficiency

On our benchmarks, Tovek V2.1 is the fastest Tovek yet, and it matches or improves on V2 in every correctness suite we run. Where a version can’t read a bytecode format at all, the table says so instead of counting it as a zero.

The one measure where V2.1 gives a little ground is source structure: its output follows the original’s shape very slightly less closely than V2’s (0.861 against 0.866). That is the price of the exactness fixes described under Correctness below, and it is one of the first things the next updates will win back.

Where V2.1’s advantage is clearest is speed. It removes a great deal of repeated work across the pipeline, from reading bytecode to naming variables, which adds up to a game decompiled in a little over half the time.

Speed

Most people meet a decompiler in one of two ways: a whole game at once, from a SaveInstance dump, or one script at a time through the local server. V2.1 is faster at both.

For a whole game, V2.1 gets more out of every thread. On one thread it decompiles 346 scripts per second, against 198 for V2, which means V2.1 on one thread is faster than V2 on two. With 24 threads it passes 4,000 scripts per second, so the entire test game takes less than a second.

For single scripts, the gains are largest exactly where waiting hurts. Through the local server, a typical script comes back in 2.5 milliseconds instead of 3.3, and the largest script in the game, an 83 KB lightning-effects module, returns in 76 milliseconds instead of 113. A 40 KB network buffer encoder is 2.5× faster.

Ready for bytecode v14

Luau keeps evolving, and the bytecode format moves with it. Version 14 adds a fast path for protected calls: the compiler now evaluates the arguments first and fetches pcall or xpcall last. V2 couldn’t read these files at all.

V2.1 reads v14 directly and puts every protected call back the way it was written. Read naïvely, the new instruction order would turn each pcall(require, module) into a stray local require2 = require; V2.1 recognises the pattern and leaves the call alone. Across our 513 public source profiles, the v14 output matches the v12 output in 512 and is cleaner in the last one.

Reliability

A decompiler reads files from all kinds of places: executor dumps, old exports, files cut short on the way to disk. V2.1 now checks every instruction before any analysis starts. Jump targets, registers, constants, upvalues and table indices all have to make sense, and so do the sizes and counts that describe them.

When they don’t, you get a precise message instead of a silent exit, or worse, plausible-looking code built from nonsense. We fed all three versions the same 1,500 damaged copies of real scripts from the test game. V2 and v0.9 beta aborted on 104 and 105 of them; V2.1 aborted on none.

Correctness

The most important change in V2.1 is also the least visible. Code that used to look right and act wrong now does both right.

Every example below is real. We compiled the original script, decompiled it with V2 and with V2.1, and then ran all three in the Luau VM:

Tovek V2

Original Luaulocal function makeCounter() local count = 1 local function bump() count = 2 return 3 end local before = count return bump(), before end return makeCounter
return function()
    local v = 1
    return (function()
        v = 2
        return 3
    end)(), v
end
DiffersReturns 3, 2 for makeCounter()(). The original returns 3, 1. V2 reads count after bump() has already changed it.

Tovek V2.1

Original Luaulocal function makeCounter() local count = 1 local function bump() count = 2 return 3 end local before = count return bump(), before end return makeCounter
return function()
    local v = 1
    local v2 = v
    return (function()
        v = 2
        return 3
    end)(), v2
end
SameReturns 3, 1 for makeCounter()(). Like the original: the value is saved before the call.

Being exact has a small cost in brevity. Where a friendlier spelling could change behaviour, V2.1 now writes what the bytecode actually does. A vector constant is built with vector.create rather than Vector3.new, and math.pi appears as 3.141592653589793, because a script can replace Vector3 or math, and V2’s guesses would then be wrong. Across the test game, 1,741 of 3,978 files change and total output grows by 2.2%. The friendlier spellings will return wherever we can prove they are safe.

Built to be trusted

Hostile input

Every bytecode file now passes a validator before analysis. It checks each operand against the function it belongs to and names the exact prototype and instruction when something is out of range. Sizes and counts that would overflow are rejected rather than wrapped around, and an internal error that does slip through is caught and reported as a message. In batch and server mode the remaining scripts carry on.

The local server

The HTTP server runs up to four decompilations at a time across all of its routes. Everything else waits its turn in a first-come, first-served queue, and a waiting request costs almost nothing: its upload stays unread until a slot frees, so a burst of thousands of scripts from a SaveInstance dump is simply worked through in order.

Only a queue that is already full (1,024 waiting requests by default) or a wait longer than two minutes is turned away, with 503 and a Retry-After hint that the bundled executor scripts follow automatically. Both limits can be changed with TOVEK_QUEUE_LIMIT and TOVEK_QUEUE_TIMEOUT_SECS. Once a request is admitted, its upload has 30 seconds to arrive in full; a client that trickles bytes gets 408 (TOVEK_UPLOAD_TIMEOUT_SECS). Identical scripts inside one batch are decompiled once.

Same output, every time

V2.1 writes byte-identical output whether it runs on one thread or twenty-four, and every speed-up in this release was checked to leave the output of all 3,978 scripts in the test game unchanged. Tovek runs entirely on your machine with deterministic rules: no network access, no AI models, nothing that changes from one run to the next.

Checked before release

V2.1 passes more than 1,200 workspace tests, all 252 runtime profiles at bytecode v9, v12 and v14, all 513 public source profiles at v12 and v14, and the full deep-review suite. These checks cover the programs we tested; they don’t prove equivalence for every possible script, and we have not run a complete game inside Roblox. Bytecode also can’t bring back comments, or names that were stripped before it was saved.

What’s next

V2.1 is a foundation. The next major updates will follow in the coming weeks, and they are much bigger:

  1. Coming weeks

    Cleaner code

    Tighter output wherever Tovek still writes more than the original author did: fewer temporaries, if-expressions where they read better, and the friendly spellings back wherever they are provably safe.

  2. Coming weeks

    Names that travel

    Names learned in one function or module carried into the code that uses it, so far fewer values are left anonymous.

  3. Coming weeks

    Faster again

    Another round of performance work, aimed squarely at the largest scripts.

  4. Next

    V3: whole projects

    Decompiling a game as one project rather than a pile of separate scripts, following requires across modules and checking the result against real Roblox behaviour.

Availability

Tovek V2.1 is available now for Windows and Linux from GitHub Releases. Each download includes the command-line decompiler, the local HTTP server and the executor client scripts. To check your copy, run luau-lifter --version, which prints luau-lifter V2.1.1.
