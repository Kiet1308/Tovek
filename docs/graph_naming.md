# Bounded role propagation on the final binding graph

The final pass renames local bindings after all expression/cleanup transformations. It never changes fields, globals, string constants, operators, statements, annotations or capture identity. Recorded source names and method receivers are protected; scope constraints reserve globals and interfering local names before assigning suffixes. Candidate ties, unknown ownership and budget exhaustion preserve the previous name.

Role edges cover immutable local copies, literal field reads/writes and record values, exact local call argument positions, fixed scalar helper result tuples and adjacent private assignment diamonds. A helper is resolved only through a unique owned closure declaration with exactly one write across the whole graph, including nested functions. A Ref capture alone does not reassign that function; an actual rebind anywhere refuses the edge. Value-copy propagation retains the stricter captured-cell veto.

Helper results must come from a straight-line body ending in a fixed tuple of local or literal-field reads. Local result sources must be immutable; a direct field supplies a naming role and no value/effect proof. The receiving assignment must have matching arity and a fixed argument pack. Assignment-position Select::Call represents a fixed multi-result bytecode call and is handled according to the formatter's assignment contract. Open result packs, branches, variadic bodies, mutable result bindings and unresolved callees are refused. Existing inlining can eliminate an intermediate field local; direct return-field roles preserve this naming opportunity without moving the field evaluation.

A diamond requires an immediately preceding empty/nil declaration, two single-assignment arms to that binding, exactly three total writes and no captured-cell ambiguity. Both immutable input bindings must agree on one strongest role. This recognizes a role consensus and does not reconstruct an initializer expression, merge storage or authorize evaluating both arms.

`naming_api.rs` versions the exact buffer API member/argument table against the pinned Luau VM source. Buffer offset/count, bit positions, copy source/target positions and string arguments remain inferred role context. Unknown similarly prefixed API names no longer inherit a role merely from read*/write*. Metadata does not establish runtime API identity, type, purity, totality, error behavior or availability of a feature-flagged member.

Analysis records compiler-derived parameter annotations and type naming hints separately from inferred naming candidates. A numeric type alone never supplies a domain name such as price/damage/duration. No source alias, generic or complex annotation is invented. Metadata priorities are ordinal evidence, not probabilities.

The graph retains the existing limits of 100,000 visited nodes, 50,000 bindings, depth 256, 24 candidates per binding and four propagation rounds. Empty or conflicting proof/context takes the unchanged-name path. The legacy candidate audit is independently bounded and holds no local owners during earlier cleanup.

The [acceptance inventory](roadmap_v2_acceptance/roles_validation.json) records runtime, alpha equivalence, source metrics, bytecode/debug metadata preservation, determinism and measured cost. [Before/after examples](roadmap_v2_acceptance/roles_examples.json) and a [reader review sheet](role_naming_review.md) distinguish role quality from exact spelling. Source-aligned exact names improve on development and are unchanged on holdout; the user judged the three submitted role examples clearer. This limited qualitative feedback is not a general role-accuracy score. Broader control-flow summaries and automatic use of project-wide module summaries remain outside these rules.
